# ClaimFlow

A claims platform for motor and property claims: claimants report and track claims, claims staff assess and decide them, and team leads see workload and outstanding exposure. Take-home assessment build; backend first.

> Local only. Not hosted publicly. No client branding or proprietary material is used.

## Stack

| Part | Choice |
| --- | --- |
| Backend | Java 21, Spring Boot 4, Spring Data JPA, Flyway, PostgreSQL 17 |
| Events | Spring Modulith event publication registry (transactional outbox) + Kafka externalization; Kafka 4.1 single-node KRaft |
| Services | `claims-service` (system of record, REST, port 8080) and `notification-service` (Kafka consumer, port 8081) |
| Frontend | Angular 22 (`web/`) |
| Contract | OpenAPI from springdoc, exported to `docs/api/openapi.yaml`; Angular client generated from it |
| Tests | JUnit 5, Spring Modulith module tests, Testcontainers |

## Run locally

Prerequisites: Docker, JDK 21, Maven 3.9+, Node 22.22.3+ or 24.15+ (for the Angular 22 CLI).

```bash
# 1. Infrastructure (Postgres + Kafka)
docker compose up -d

# 2. Backend services (two terminals)
mvn -pl claims-service spring-boot:run
mvn -pl notification-service spring-boot:run

# 3. Frontend
cd web && npm install && npm start      # http://localhost:4200
```

Or run everything except the frontend in containers:

```bash
docker compose --profile app up -d --build
```

Useful URLs: Swagger UI http://localhost:8080/swagger-ui.html · health http://localhost:8080/actuator/health · notifications Swagger UI http://localhost:8081/swagger-ui.html

Watch claim events on Kafka (envelope, topic, delivery guarantee and failure demo: [`docs/events.md`](docs/events.md)):

```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic claims.events --from-beginning --property print.key=true --property print.headers=true
```

`mvn verify` also runs the Testcontainers integration tests (`*IT`), so Docker must be running.

## API

Every request carries `X-User-Id` (a seeded user id, see below). Errors are RFC 9457 problem details. Commands carry the `version` the client last read (optimistic locking, 409 if stale).

| Method | Path | Who | What |
| --- | --- | --- | --- |
| POST | `/api/v1/claims` | claimant | Submit a claim (`Idempotency-Key` header optional; 201, or 200 on replay) |
| GET | `/api/v1/claims/mine` | claimant | My claims, newest first |
| GET | `/api/v1/claims/{id}` | staff, owning claimant | Claim detail with history and information requests |
| GET | `/api/v1/claims?unassigned=&assignee=&status=` | staff | Work queue, an officer's claims, or claims by status |
| POST | `/api/v1/claims/{id}/assign` | officer (self), lead | Pick up or reassign |
| POST | `/api/v1/claims/{id}/info-requests` | assigned officer, lead | Ask the claimant for information |
| POST | `/api/v1/claims/{id}/info-requests/{requestId}/response` | owning claimant | Answer it |
| PUT | `/api/v1/claims/{id}/reserve` | assigned officer, lead | Set the reserve during assessment |
| POST | `/api/v1/claims/{id}/decision` | assigned officer, lead | Approve (amount) or reject (reason) |
| POST | `/api/v1/claims/{id}/settle` | assigned officer, lead | Mark an approved claim settled |
| POST | `/api/v1/claims/{id}/withdraw` | owning claimant | Withdraw before a decision |
| GET | `/api/v1/metrics/workload` | officer, lead | Queue, waiting on claimant, SLA breaches, per-officer load |
| GET | `/api/v1/metrics/exposure` | lead | Sum of reserves on open claims per market, in its currency |
| GET | `/api/v1/notifications/mine` | anyone (port 8081) | My notifications, newest first |
| POST | `/api/v1/notifications/{id}/read` | recipient (port 8081) | Mark a notification read |

Try them with Swagger UI or [`docs/api/claims.http`](docs/api/claims.http) (IntelliJ HTTP Client, runs top to bottom).

### API contract

The OpenAPI contract for the frontend is generated by springdoc and committed as [`docs/api/openapi.yaml`](docs/api/openapi.yaml). Re-export it after changing an endpoint, with claims-service running on :8080:

```bash
curl http://localhost:8080/v3/api-docs.yaml -o docs/api/openapi.yaml
```

## Frontend

Angular 22 (standalone components, signals, lazy routes guarded by role), plain SCSS, no UI component library.

**Run it.** Start Postgres, Kafka and both services first (see [Run locally](#run-locally)), then:

```bash
cd web
npm install
npm start          # http://localhost:4200, proxies /api/v1/notifications to :8081 and /api to :8080
```

Needs Node 22.22.3+ or 24.15+ (the Angular 22 CLI refuses older versions). Other scripts: `npm run build`, `npm test` (Vitest component tests), `npm run api` (regenerates the typed client in `src/app/api/` from `docs/api/openapi.yaml` with ng-openapi-gen; re-export the contract first if an endpoint changed).

**Pick a user** on the start page (top right "Switch user" changes it any time):

| To try | Pick | Where |
| --- | --- | --- |
| Report a claim, follow it, answer a question, withdraw | Alice Tan or Raj Kumar | "Report an incident", "My claims", the bell for notifications |
| Pick up a claim, request information, set the reserve, approve or reject, settle | Ben Lim or Chitra Nair | "Queue" → Pick up → workbench; "My claims" for assigned work |
| Reassign claims, see all open claims, workload and exposure | Daniel Wong | "Open claims" (status filter), workbench "Reassign", "Dashboard" |

Full lifecycle in about two minutes: Alice reports an incident → Ben picks it up from the queue and requests information → Alice replies from the notification → Ben sets the reserve, approves and settles → Alice sees "Settled" and her notifications.

How it behaves:
- Action buttons come from the claim's `allowedNext` and the user's role, as returned by the API; the UI does not re-implement the lifecycle (ADR-13).
- Every command sends the version of the claim on screen. If someone else changed it, the API's "changed by someone else" message is shown and the claim reloads.
- Lists, claims, notifications and the dashboard refresh every 15 s while the tab is visible, and right away when you come back to the tab (ADR-14).
- Errors from the API are shown as dismissible banners with the problem details from the server. Claimants never see the reserve.

Claim lifecycle: `SUBMITTED → UNDER_REVIEW ⇄ INFO_REQUESTED → APPROVED → SETTLED`, with `REJECTED` from review and `WITHDRAWN` before a decision.

## Assumptions

- Policy numbers are free text; policy validation is stubbed.
- Six markets are configuration (SG, MY, HK, AU, TH, ID), each with its own currency. Exposure is never summed across currencies.
- One officer owns a claim at a time; leads can reassign.
- Open claims older than 10 days count as SLA breaches (`claimflow.sla-days`).


## What I prioritised, and what is not built (and why)

The brief asks for ruthless prioritisation, so I built depth on the backend first: a complete, tested claim lifecycle with reliable events beats a wide but shallow UI.

**Built**
- Full claim lifecycle API with an explicit state machine, role checks, optimistic locking, idempotent submission and RFC 7807 errors.
- Domain events stored in a transactional outbox (Spring Modulith) and published to Kafka, keyed by claim for per-claim ordering.
- Notification service consuming those events, with deduplication and a dead-letter topic.
- Workload and exposure metrics for staff.
- Angular app: claimant flow and officer workbench. _(edit: add the lead dashboard if finished)_

**Not built, deliberately**

| Item | Why not | What I would do next |
| --- | --- | --- |
| Real authentication | Out of the time box; roles are still enforced via a stubbed `X-User-Id` header | OIDC (e.g. Keycloak) with JWTs; map roles from token claims |
| Document and photo upload | Storage and virus scanning add infrastructure without showing new design | Object storage with pre-signed URLs; metadata on the claim |
| Payments | Settlement is recorded, not paid | Integrate a payments service as another event consumer |
| FX conversion for exposure | Summing across currencies would be wrong without rates | A rates source and a reporting currency, clearly labelled |
| Live updates (SSE / WebSocket) | Polling every 15 s is enough at demo scale | SSE from a small read service fed by `claims.events` |
| Paging and search | Demo data volumes | `Pageable` on list endpoints, indexed filters |
| Production Kafka setup | Single local broker | 3 brokers, replication factor 3, `min.insync.replicas=2`, schema registry |
| Separate read model for metrics | SQL aggregates are correct and real-time at this scale | Event-fed reporting service consuming `claims.events` |
